# 02. PRD / 기획서 Copilot으로 초안 만들기

## 학습 목표

- Copilot Instruction 파일로 회사 PRD 형식을 학습시키는 방법을 안다
- PRD의 각 섹션을 Copilot 프롬프트로 생성하고 검토하는 흐름을 익힌다
- 가상 제품 PRD를 처음부터 끝까지 직접 작성한다

**예상 소요**: 60분 (이론 20분 + 실습 40분)

---

## 2.1 PRD란 무엇이고 왜 어려운가

PRD(Product Requirements Document)는 "이 기능을 왜, 무엇을, 어떻게 만들 것인가"를 정리한 문서입니다. 팀 전체의 기준 문서이자, 개발/디자인/마케팅 모두가 참조하는 단일 출처(single source of truth)입니다.

PRD 작성이 어려운 이유는 크게 세 가지입니다.

첫째, 빈 화면 앞의 두려움입니다. 무엇부터 써야 할지 모릅니다.
둘째, 형식이 없으면 매번 다른 구조로 만들어져서 팀 간 소통이 어렵습니다.
셋째, 놓친 섹션이나 모호한 표현 때문에 개발 중에 "이건 기획서에 없는데요"라는 상황이 생깁니다.

Copilot은 이 세 가지를 모두 해결해줍니다.

---

## 2.2 PRD의 7가지 핵심 섹션

잘 쓰인 PRD에는 아래 7개 섹션이 반드시 포함됩니다.

| # | 섹션 | 핵심 질문 | 놓쳤을 때 발생하는 문제 |
|---|------|-----------|------------------------|
| 1 | 배경 및 문제 정의 | 왜 이걸 만드는가? | 개발팀이 "왜 이걸 만드는지 모르겠다"고 함 |
| 2 | 목표 및 성공 지표 | 성공이 무엇인가? | 출시 후 "잘 됐나 안 됐나" 판단 기준 없음 |
| 3 | 사용자 스토리 | 누가 어떻게 쓰는가? | 엣지케이스 누락, QA에서 버그 발견 |
| 4 | 기능 명세 | 정확히 무엇을 만드는가? | 개발팀이 다르게 구현 |
| 5 | 비기능 요구사항 | 성능/보안/접근성? | 출시 후 성능 이슈, 보안 취약점 |
| 6 | 스코프 (In/Out) | 이번에 할 것 vs 안 할 것 | 스코프 크리프, 일정 지연 |
| 7 | 리스크 및 일정 | 무엇이 위험하고 언제 끝나나? | 예상치 못한 지연, 이해관계자 불만 |

---

## 2.3 Copilot Instruction 파일로 회사 형식 학습시키기

Copilot은 `.github/copilot-instructions.md` 파일을 **자동으로 맥락에 포함**합니다.
이 파일에 회사 PRD 형식, 용어, 규칙을 정의해두면 매번 설명할 필요가 없어집니다.

### 설정 방법

VS Code에서 작업 폴더(예: `pm-workspace`)를 열고, 이 위치에 파일을 만듭니다:

```
pm-workspace/
└── .github/
    └── copilot-instructions.md
```

### Instruction 파일 예시

```markdown
# PM 기획 작업 공간 — Copilot 지시사항

## 문서 형식
- 모든 문서는 Markdown으로 작성
- 제목: ## 대제목, ### 소제목
- 코드/변수명은 영어, 본문은 한국어
- 표는 반드시 Markdown 표 문법 사용

## PRD 작성 규칙
- 회사 PRD 형식: 배경/목표/사용자스토리/기능명세/비기능요구사항/스코프/리스크/일정
- 성공 지표는 반드시 측정 가능한 수치로 (예: "증가" 대신 "20% 증가")
- 스코프 섹션에는 In-Scope와 Out-of-Scope 모두 명시
- 리스크는 발생 가능성과 영향도를 함께 표기

## 사용자 스토리 형식
- As a [사용자 유형], I want to [행동], so that [목적/가치].
- 인수 조건은 Given-When-Then 형식

## 용어 규칙
- "사용자" = 앱 실사용자
- "운영자" = 내부 관리자
- 우선순위: Highest > High > Medium > Low
- 타입: Story / Task / Bug / Spike

## 금지 표현
- "적절히", "빠르게", "충분히" — 반드시 수치로 대체
- "등", "및 기타" — 구체적으로 열거
```

이 파일을 저장하면, 이후 Copilot은 자동으로 이 규칙을 따릅니다.

## 2.4 섹션별 Copilot 프롬프트 전략

PRD 전체를 한 번에 생성하는 것보다, **섹션별로 나눠서** 생성하는 것이 품질이 높습니다.

### 전략 1: 골격 먼저, 내용 나중

**Step 1 — 구조 생성**

```
"AI 학습 기록 앱"의 스트릭(학습 연속 일수) 기능 PRD 골격을 만들어줘.
섹션: 배경/목표/사용자스토리/기능명세/비기능요구사항/스코프/리스크/일정.
각 섹션은 제목만 만들고, 내용 자리에 [채워야 할 내용 설명] 형식의 플레이스홀더 표시.
```

**Step 2 — 섹션별 내용 생성**

```
위 PRD의 "배경 및 문제 정의" 섹션 내용을 채워줘.
포함 내용:
- 현황 (학습 앱 사용자 이탈 문제)
- 가설 (스트릭이 재방문율에 영향을 준다는 근거)
- Why Now (경쟁사 Duolingo 사례 언급)
```

### 전략 2: BAD vs GOOD 프롬프트 비교

| | 프롬프트 | 결과 |
|---|----------|------|
| ❌ BAD | "PRD 써줘" | 뻔한 구조, 내용 없음 |
| ❌ BAD | "스트릭 기능 PRD 만들어줘" | 구조는 있지만 맥락 없음 |
| ✅ GOOD | 아래 참조 | 맥락 있는 실용적 초안 |

**GOOD 프롬프트 전체 예시**:

```
"AI 학습 기록 앱 (가칭: LearnLog)"의 학습 스트릭 기능 PRD 초안을 작성해줘.

제품 배경:
- LearnLog는 사용자가 매일 학습 내용을 기록하는 앱
- 현재 Day 7 이후 이탈율이 40%로 높음
- 스트릭(연속 학습 일수) 기능으로 습관 형성 유도 예정

기능 목적:
- 사용자가 매일 앱을 열게 만드는 게임화 요소
- 학습 연속 일수를 시각적으로 보여주고 달성 시 보상 제공

대상 사용자:
- 자기계발에 관심 있는 20~35세 직장인

다음 섹션을 포함한 Markdown PRD 초안:
1. 배경 및 문제 정의
2. 목표 (성공 지표 3개, 측정 가능한 수치)
3. 사용자 스토리 (5개)
4. 기능 명세 (10개 항목)
5. 비기능 요구사항 (성능/보안 각 2개)
6. 스코프 (In-Scope 5개, Out-of-Scope 3개)
7. 리스크 (3개, 발생가능성+영향도+대응방안)
8. 마일스톤 (3단계 표)
```

## 2.5 각 섹션 작성 시 주의사항

### 목표 및 성공 지표 섹션

Copilot이 자주 만드는 실수: "사용자 만족도 향상"처럼 측정 불가한 목표를 씁니다.

반드시 이렇게 후속 프롬프트를 쓰세요:

```
위 목표 섹션에서 측정 불가한 표현을 모두 찾고, 각각을 측정 가능한 수치 목표로 바꿔줘.
예: "사용자 만족도 향상" → "NPS 점수 현재 42 → 55 달성 (3개월 내)"
```

### 기능 명세 섹션

기능 명세가 너무 추상적으로 나오면:

```
기능 명세의 각 항목을 개발자가 바로 구현할 수 있을 수준으로 구체화해줘.
"스트릭 표시" → "홈 화면 상단에 불꽃 아이콘과 함께 연속 학습 일수 숫자 표시.
                  당일 학습 완료 시 강조 애니메이션. 미완료 시 회색 처리."
같은 수준으로.
```

### 스코프 섹션

Out-of-Scope를 빠뜨리는 경우가 많습니다. 이렇게 요청하세요:

```
이 기능의 Out-of-Scope 항목을 5개 더 추가해줘.
개발팀이 "이것도 만들어야 하나요?"라고 물어볼 수 있는 항목 위주로.
각 항목 옆에 Out-of-Scope인 이유 한 줄씩.
```

## 2.6 PRD 검토 및 개선

초안이 만들어졌으면, 다음 프롬프트로 품질을 높입니다.

**논리 흐름 검토**:

```
위 PRD를 시니어 PM 관점에서 검토해줘.
다음 4가지를 확인해줘:
1. 문제 정의와 솔루션이 논리적으로 연결되는가
2. 성공 지표가 기능 목적과 연결되는가
3. 사용자 스토리가 기능 명세를 커버하는가 (커버 안 되는 것이 있다면 표시)
4. 리스크 대응이 현실적인가

문제점을 발견하면 개선 방안도 함께 제시.
```

**엣지케이스 추가**:

```
위 PRD의 기능 명세에서 놓친 엣지케이스를 찾아서 추가해줘.
특히:
- 최초 사용자 (스트릭이 0인 상태)
- 스트릭이 깨진 후 재시작
- 앱을 며칠 안 켜다가 다시 켰을 때
- 시간대가 다른 경우 (해외 여행 중 날짜 변경)
```

## 실습

### 실습 1. Instruction 파일 만들기

VS Code에서 새 폴더 `pm-workspace`를 만들고, `.github/copilot-instructions.md` 파일을 생성하세요.

다음 내용을 직접 입력해보세요 (복붙이 아닌 직접 입력하면서 Tab 자동완성을 경험):

```markdown
# PM 기획 작업 공간 — Copilot 지시사항

## PRD 작성 규칙
- 섹션 순서: 배경 → 목표 → 사용자스토리 → 기능명세 → 스코프 → 리스크 → 일정
- 성공 지표는 측정 가능한 수치 사용 (퍼센트, 절대값, 기간 명시)
- 스코프 섹션에 In-Scope와 Out-of-Scope 모두 포함
```

저장 후, `test-prd.md` 파일을 새로 만들고 Chat에 짧게 요청해보세요:

```
다크 모드 지원 기능의 PRD 골격을 만들어줘.
```

Instruction 파일이 없을 때와 있을 때 결과가 어떻게 다른지 비교해보세요.

### 실습 2. 가상 제품 PRD 작성 A~Z

아래 제품/기능 조건으로 PRD 전체를 작성해보세요.

**소재**: AI 학습 기록 앱 "LearnLog"의 **소셜 챌린지** 기능
- 친구와 함께 학습 목표를 설정하고 서로의 진행상황을 볼 수 있는 기능
- 최대 5명 그룹 챌린지

**단계**:

1. `learnlog-challenge-prd.md` 파일 생성
2. 파일 상단에 다음 컨텍스트 주석 추가:

```markdown
<!--
제품: LearnLog (AI 학습 기록 앱)
기능: 소셜 챌린지
목적: 학습 지속성 향상을 위한 소셜 동기 부여
대상 사용자: 20~35세, 혼자 공부하다 포기하는 패턴의 직장인
-->
```

3. Chat에 GOOD 프롬프트 형식으로 PRD 초안 요청 (2.4절 참고)
4. 생성된 초안에서 다음을 수정:
   - 성공 지표 중 측정 불가한 항목 찾아서 수치화
   - Out-of-Scope 항목 3개 추가
   - 리스크에 "소셜 기능 특유의 리스크" (신고/차단, 개인정보, 그룹 알림 스팸) 추가

5. "PRD 검토 요청" 프롬프트로 품질 검토 후 최종 수정

### 실습 3. 회사 실제 기획서로 적용 (선택)

현재 진행 중인 기획이 있다면, 그 기획의 일부 섹션(예: 사용자 스토리 5개)을 Copilot으로 재생성해보세요.

기존에 작성한 버전과 Copilot 생성 버전을 나란히 두고 비교합니다:
- 어떤 부분이 더 낫나요?
- Copilot이 놓친 맥락은 무엇인가요?
- 어떤 내용은 바로 가져다 쓸 수 있나요?

---

## 핵심 포인트

1. `.github/copilot-instructions.md` 파일로 회사 PRD 형식을 한 번 등록하면, 이후 모든 PRD에서 형식이 자동 적용됩니다
2. PRD 전체를 한 번에 생성하기보다 **골격 먼저, 섹션별 내용 생성** 전략이 품질이 높습니다
3. Copilot이 만드는 가장 흔한 실수는 **측정 불가한 목표**와 **누락된 Out-of-Scope**입니다. 생성 후 반드시 확인하세요
4. 엣지케이스 발굴은 사람이 하기 어렵고 Copilot이 잘하는 영역입니다. "놓친 엣지케이스" 프롬프트를 습관화하세요
5. 초안 생성 후 **논리 흐름 검토 프롬프트**를 한 번 더 돌리면 PRD 품질이 크게 올라갑니다
