# 03. 사용자 스토리 / 요구사항 정리

## 학습 목표

- INVEST 원칙을 이해하고 품질 좋은 사용자 스토리를 판별할 수 있다
- Gherkin(Given-When-Then) 형식으로 인수 조건을 작성할 수 있다
- Copilot으로 엣지케이스를 체계적으로 발굴할 수 있다
- 회원가입 기능의 사용자 스토리 20개 이상을 실습으로 완성한다

**예상 소요**: 50분 (이론 15분 + 실습 35분)

---

## 3.1 사용자 스토리란 무엇인가

사용자 스토리는 **사용자의 관점에서** 기능을 설명하는 짧은 문장입니다. "시스템이 무엇을 해야 한다"가 아니라 "사용자가 무엇을 원한다"는 관점이 핵심입니다.

**기본 형식**:
```
As a [사용자 유형],
I want to [행동/기능],
so that [얻는 가치/이유].
```

**실제 예시**:
```
As a 신규 가입자,
I want to 이메일과 비밀번호로 계정을 만들고 싶다,
so that 다음 방문 때 내 학습 기록에 접근할 수 있다.
```

---

## 3.2 INVEST 원칙 — 좋은 스토리의 기준

INVEST는 좋은 사용자 스토리가 갖춰야 할 6가지 속성의 약자입니다.

| 원칙 | 뜻 | 위반 예시 | 수정 방법 |
|------|-----|-----------|-----------|
| **I**ndependent | 다른 스토리와 독립적 | "회원가입 완료 후 이메일 인증" (앞 스토리 의존) | 인증 기능을 별도 스토리로 분리 |
| **N**egotiable | 세부 구현은 협상 가능 | "버튼 색상이 #3B82F6이어야 한다" | "명확히 구분되는 CTA 버튼" |
| **V**aluable | 사용자에게 가치 제공 | "DB에 사용자 테이블 생성" | 기술 작업은 Task로 별도 관리 |
| **E**stimable | 크기 추정 가능 | "사용자 경험 전반 개선" | 구체적인 기능 단위로 분해 |
| **S**mall | 한 스프린트 안에 완료 | "전체 회원 시스템 구축" | 회원가입 / 로그인 / 프로필 등으로 분리 |
| **T**estable | 테스트 가능 | "사용하기 편해야 한다" | "3단계 이내 회원가입 완료 가능" |

### Copilot으로 INVEST 검증하기

작성한 스토리를 검증할 때:

```
아래 사용자 스토리들을 INVEST 원칙 기준으로 검토해줘.
각 원칙(I/N/V/E/S/T)에 대해 만족 여부를 ✅/❌로 표시하고,
❌인 항목에 대해 개선 방안을 제시해줘.

[사용자 스토리 목록 붙여넣기]
```

## 3.3 Gherkin 형식 — 인수 조건(Acceptance Criteria)

인수 조건은 "이 스토리가 완료됐다는 것을 어떻게 확인하는가"를 정의합니다.
Gherkin 형식은 개발자·QA·PM이 공통으로 이해할 수 있는 표준 형식입니다.

**형식**:
```gherkin
Feature: [기능명]

  Scenario: [시나리오 이름]
    Given [초기 상태 / 사전 조건]
    When  [사용자 행동]
    Then  [기대되는 결과]
```

**예시 — 이메일 회원가입**:
```gherkin
Feature: 이메일 회원가입

  Scenario: 정상적인 회원가입 성공
    Given 사용자가 회원가입 페이지에 있다
    When  유효한 이메일과 8자 이상의 비밀번호를 입력하고 가입 버튼을 누른다
    Then  인증 이메일이 발송되고 "이메일을 확인해주세요" 안내 화면이 표시된다

  Scenario: 이미 사용 중인 이메일로 가입 시도
    Given 사용자가 회원가입 페이지에 있다
    When  이미 가입된 이메일 주소를 입력하고 가입 버튼을 누른다
    Then  "이미 사용 중인 이메일입니다" 에러 메시지가 표시된다
    And   비밀번호 찾기 링크가 함께 노출된다

  Scenario: 비밀번호가 요건 미충족
    Given 사용자가 회원가입 페이지에 있다
    When  7자 이하의 비밀번호를 입력한다
    Then  "비밀번호는 8자 이상이어야 합니다" 안내 문구가 실시간으로 표시된다
    And   가입 버튼이 비활성화 상태를 유지한다
```

### Copilot으로 Gherkin 생성하기

```
아래 사용자 스토리의 인수 조건을 Gherkin Given-When-Then 형식으로 작성해줘.

사용자 스토리:
As a 신규 사용자, I want to 이메일과 비밀번호로 가입하고 싶다,
so that 내 데이터를 저장하고 다음 방문 때 접근할 수 있다.

시나리오 포함:
- 정상 가입 (Happy Path)
- 이미 가입된 이메일
- 비밀번호 규칙 위반 (길이 / 특수문자 미포함 / 공백 포함)
- 이메일 형식 오류
- 네트워크 오류 중 제출
```

## 3.4 Copilot으로 엣지케이스 체계적으로 발굴하기

PM이 혼자 엣지케이스를 생각하면 반드시 놓치는 부분이 생깁니다. Copilot은 체계적으로 여러 관점에서 엣지케이스를 뽑아줍니다.

### 엣지케이스 발굴 5가지 관점

| 관점 | 예시 질문 |
|------|----------|
| 입력값 경계 | 비어있으면? 너무 길면? 특수문자면? |
| 권한 경계 | 비로그인 접근? 다른 사람 데이터 접근? 권한 없는 관리자? |
| 동시성 | 두 탭에서 동시 제출? 같은 이메일로 두 명이 동시 가입? |
| 네트워크/시스템 | 제출 중 인터넷 끊김? 서버 느림? 재시도? |
| 비즈니스 규칙 | 탈퇴한 계정 재가입? 소셜 로그인과 이메일 같은 주소 충돌? |

### 엣지케이스 발굴 프롬프트

```
회원가입 기능에서 PM이 놓치기 쉬운 엣지케이스를 발굴해줘.

기능 개요: 이메일/비밀번호 회원가입, 이메일 인증 필수, 소셜 로그인(구글/카카오) 연동

5가지 관점에서 각 3개 이상:
1. 입력값 경계 (길이 제한, 특수문자, 공백, 인코딩)
2. 권한 경계 (비로그인, 중복, 탈퇴 후 재가입)
3. 동시성 (동일 이메일 동시 요청, 여러 탭)
4. 네트워크/시스템 (느린 연결, 인증 메일 미도착, 링크 만료)
5. 비즈니스 규칙 (소셜 계정과 이메일 충돌, 관리자가 특정 이메일 차단)

각 엣지케이스를 "시나리오 / 기대 동작 / 기획서 반영 필요 여부" 형식으로.
```

## 3.5 요구사항 명세서 작성 흐름

사용자 스토리 → 기능 요구사항 명세서로 발전시키는 흐름입니다.

```
사용자 스토리 (What + Why)
    ↓
인수 조건 (How to verify)
    ↓
기능 요구사항 (Functional Requirements)
    ↓
비기능 요구사항 (Non-Functional Requirements)
```

### 요구사항 명세서 Copilot 생성 예시

```
아래 사용자 스토리와 인수 조건을 기반으로 기능 요구사항 명세서를 작성해줘.

사용자 스토리: [붙여넣기]
인수 조건: [붙여넣기]

출력 형식 (각 요구사항):
- 요구사항 ID: FR-001 형식
- 분류: 기능적 (Functional)
- 우선순위: Highest / High / Medium / Low
- 설명: 주어+동사 형태로 명확하게 (1문장)
- 인수 조건: Given-When-Then 1개
- 연관 스토리 ID

비기능 요구사항 (NFR)도 별도로:
- 성능: 응답 시간
- 보안: 비밀번호 암호화, HTTPS
- 접근성: 키보드 탐색 가능
```

## 3.6 사용자 스토리 분할 기법

스토리가 너무 크면(에픽 수준) 분할해야 합니다. Copilot이 잘 도와주는 영역입니다.

### 분할 기법 4가지

| 기법 | 예시 |
|------|------|
| **워크플로우 단계별** | "회원가입" → 폼 입력 / 이메일 인증 / 프로필 설정 |
| **사용자 유형별** | "알림 설정" → 일반 사용자용 / 관리자용 |
| **데이터 유형별** | "파일 업로드" → 이미지만 / 이미지+문서 / 동영상 포함 |
| **성능 수준별** | "검색" → 기본 텍스트 검색 / 필터 검색 / 실시간 검색 |

**분할 요청 프롬프트**:

```
아래 사용자 스토리가 너무 크다(에픽 수준). INVEST 원칙을 지키면서
한 스프린트(2주, 스토리포인트 5 이하)에 완료 가능한 단위로 분할해줘.

원본 스토리: [붙여넣기]

분할 기준:
- 각 스토리가 독립적으로 가치를 제공해야 함
- 구현 순서 의존성이 있다면 표시
- 분할 후 스토리 수: 3~5개

각 스토리에 추정 스토리포인트도 제안.
```

### 실습 1. 회원가입 기능 사용자 스토리 20개 생성

```
모바일 앱의 회원가입 기능 사용자 스토리를 작성해줘.

앱 개요: AI 학습 기록 앱 "LearnLog"
가입 방식: 이메일/비밀번호, 구글 소셜 로그인, 카카오 소셜 로그인

사용자 유형:
- 신규 방문자 (앱 처음 사용)
- 기존 사용자 (로그인 페이지에서 회원가입 링크 클릭)
- 탈퇴 후 재가입 시도 사용자

다음 카테고리별로 각각 스토리 작성:
1. 이메일/비밀번호 가입 (정상 흐름) — 4개

4. 에러 케이스 (중복 이메일, 형식 오류 등) — 4개
5. 보안/권한 관련 — 3개
6. 비즈니스 규칙 엣지케이스 — 3개

형식: As a [사용자 유형], I want to [행동], so that [가치].

```

생성된 스토리 목록을 보고:
- INVEST 위반 사례 찾기

- 누락된 시나리오 추가

## 핵심 포인트

1. **INVEST 원칙**은 좋은 스토리의 6가지 기준입니다. 특히 V(가치 있어야)와 T(테스트 가능해야)를 자주 확인하세요
2. **Gherkin Given-When-Then**은 개발·QA·PM이 공통 언어로 소통하는 인수 조건 형식입니다. 특히 에러 케이스 시나리오를 반드시 포함하세요
3. Copilot은 **엣지케이스 발굴**에 특히 강합니다. 5가지 관점(입력/권한/동시성/네트워크/비즈니스 규칙) 프롬프트를 습관화하세요
4. 사용자 스토리가 너무 크면 **4가지 분할 기법** 중 하나로 쪼개고, 각 분할 스토리가 독립적으로 가치를 제공하는지 확인하세요
5. Copilot이 생성한 인수 조건에 **"적절히", "빠르게"** 같은 모호한 표현이 있으면 반드시 수치로 교체하세요
