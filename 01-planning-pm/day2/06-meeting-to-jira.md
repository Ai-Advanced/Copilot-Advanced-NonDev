# 06. 회의록 → JIRA/Notion 티켓 자동화

## 학습 목표

- 회의록 Markdown을 JIRA 티켓 초안으로 변환하는 프롬프트 패턴을 익힌다
- 티켓 유형(Story/Task/Bug/Spike) 구분 기준을 이해한다
- 우선순위, 담당자, 스토리 포인트 자동 태깅 프롬프트를 쓸 수 있다
- 실제 회의록 예시 하나에서 티켓 8개를 생성하는 실습을 완료한다

**예상 소요**: 50분 (이론 15분 + 실습 35분)

---

## 6.1 왜 이 작업이 귀찮고 시간이 걸리는가

스크럼 회의 한 번이 끝나면 PM 앞에 이런 작업이 기다립니다:

1. 회의록 다시 읽기 (10분)
2. 액션 아이템 추출 (10분)
3. JIRA 창 열기, 티켓 제목 입력 (5분)
4. 각 티켓 설명 작성 — 이 부분이 가장 오래 걸림 (30~40분)
5. 타입, 우선순위, 담당자, 에픽 연결 (10분)

8개 티켓이면 1시간이 넘습니다. 그리고 회의가 끝난 직후에 해야 하는 일이라 피로도가 높습니다.

Copilot을 쓰면 4번이 3분으로 줄어듭니다.

---

## 6.2 좋은 JIRA 티켓의 구성 요소

Copilot이 티켓을 잘 만들려면, 어떤 것이 좋은 티켓인지 먼저 알아야 합니다.

| 필드 | 설명 | 예시 |
|------|------|------|
| **제목** | 동사+목적어 형태, 한 줄로 명확하게 | "AI 코치 첫 화면 진입 로딩 상태 UI 추가" |
| **타입** | Story / Task / Bug / Spike | Story (사용자 가치 있는 기능 단위) |
| **우선순위** | Highest / High / Medium / Low | High |
| **담당자** | 실제 이름 또는 "논의 필요" | 이개발 |
| **에픽 링크** | 연관 에픽 | EP-023 AI 학습 코치 |
| **설명** | 2~3문장, 맥락 포함 | "사용자가 AI 코치 탭 진입 시..." |
| **인수 조건** | 완료 기준 2~3개 | "로딩 중 스피너 표시, 3초 내 첫 화면 표시" |
| **스토리 포인트** | 피보나치 (1/2/3/5/8/13) | 3 |

### 티켓 타입 구분 기준

| 타입 | 언제 쓰나 | 예시 |
|------|-----------|------|
| **Story** | 사용자에게 직접 가치를 전달하는 기능 단위 | "AI 학습 계획 조회 화면 구현" |
| **Task** | 기술적 작업, 사용자에게 직접 보이지 않음 | "AI 분석 API 연동 테스트" |
| **Bug** | 이미 출시된 기능의 잘못된 동작 수정 | "알림 발송 중복 버그 수정" |
| **Spike** | 기술 조사/연구 목적 (결과물: 문서 or 프로토타입) | "AI 분석 라이브러리 3종 비교 조사" |

## 6.3 회의록 → 티켓 변환 프롬프트 패턴

### 기본 패턴

```
아래 회의록에서 JIRA 티켓 초안을 추출해줘.

회의 맥락:
- 팀: [팀명]
- 현재 스프린트: [번호 or 기간]
- 연관 에픽: [에픽명 or 없음]

각 티켓 형식:
## [티켓 제목]
- **타입**: Story / Task / Bug / Spike
- **우선순위**: Highest / High / Medium / Low
- **담당자**: [이름 or "논의 필요"]
- **스토리 포인트**: [숫자 or "TBD"]
- **설명**: (2~3문장, 맥락 포함)
- **인수 조건**:
  - [ ] [조건 1]
  - [ ] [조건 2]
- **에픽**: [에픽명]

[--- 회의록 붙여넣기 ---]
```

### 우선순위 자동 판단 기준 추가

Copilot이 스스로 우선순위를 매기게 하려면 기준을 줘야 합니다:

```
우선순위 판단 기준을 적용해줘:
- Highest: 이번 스프린트 출시 블로킹 이슈
- High: 사용자 영향 크고 이번 스프린트 내 완료 목표
- Medium: 중요하지만 다음 스프린트도 가능
- Low: 있으면 좋지만 필수 아님
```

### Notion 형식으로 변환

JIRA 대신 Notion을 쓰는 팀이라면:

```
아래 회의록에서 Notion 태스크 데이터베이스 항목을 추출해줘.

Notion 속성:
- Name: 태스크 제목
- Status: Not Started / In Progress / Done
- Priority: Urgent / High / Normal / Low
- Assignee: [이름]
- Due Date: [날짜 or "미정"]
- Project: [프로젝트명]
- Description: 태스크 설명 (2~3문장)

[--- 회의록 붙여넣기 ---]
```

## 6.4 흔한 실수와 대처

⚠️ **AI가 자주 하는 실수 — 회의록 티켓 변환편**

| 실수 | 예시 | 대처 |
|------|------|------|
| 하나의 티켓에 여러 기능 묶기 | "알림 설정 UI + API 연동 + 테스트" | "한 티켓은 한 가지 작업" 명시 |
| 제목이 너무 모호함 | "알림 개선" | "동사+목적어로 제목 재작성" 후속 요청 |
| 스토리포인트 과대 추정 | 모든 티켓을 8점으로 | "1~5 범위에서 추정, 큰 작업은 분할" 명시 |
| 인수 조건이 너무 추상적 | "알림이 제대로 동작해야 한다" | "인수 조건에 '적절히' 사용 금지, 구체적 상태 기술" 명시 |
| 담당자 없이 팀명으로 | "개발팀이 해야 함" | 회의록의 실제 이름 기반으로 재생성 |

### 품질 개선 후속 프롬프트

초안이 나온 뒤 품질을 올릴 때:

```
위 티켓 초안에서 다음을 개선해줘:
1. 제목이 "명사 나열" 형태인 것을 "동사+목적어" 형태로 교체
2. 인수 조건에 "적절히", "제대로" 같은 모호한 표현을 구체적 기준으로 교체
3. Story 타입인데 사용자 가치가 없는 것을 Task로 재분류
4. 스토리포인트 8 이상인 것을 2~3개로 분할 제안
```

## 실습

### 실습 1. 기본 회의록 → 티켓 8개 생성

다음 회의록을 Chat에 붙이고 JIRA 티켓을 생성하세요.

**회의록 원본**:

```markdown
# LearnLog 스프린트 20 플래닝 회의
- 일시: 2026-07-20 오전 10시
- 참석자: 김PM (PM), 이프론트 (프론트엔드 개발자), 박백엔드 (백엔드 개발자), 최QA (QA)
- 목적: AI 학습 코치 기능 1차 출시 (Alpha) 스프린트 계획

## 논의 내용

### 1. AI 코치 탭 UI
- 이프론트: 기획서대로 하단 탭에 "코치" 탭 추가, 아이콘은 🤖 로 합의
- 탭 클릭 시 코치 메인 화면으로 이동
- 코치 메인 화면: 이번 주 학습 계획 카드 + 오늘의 동기부여 메시지 2개 섹션
- 이프론트: 데이터 없을 때 빈 상태(Empty State) UI도 필요

### 2. AI 분석 API 연동
- 박백엔드: AI 분석 서비스 연동 완료, API 문서 공유 예정
- 최소 학습 기록 7개 있어야 분석 가능 (7개 미만이면 기록 유도 메시지)
- 응답 시간이 평균 2~3초, 로딩 스피너 필요
- Rate limit 있음: 사용자당 하루 3회 새로고침 가능

### 3. 알림 기능
- 기존 알림 발송 로직에 AI 코치 타입 추가
- 매주 월요일 오전 8시 학습 계획 알림
- 오늘 학습을 안 했을 때만 저녁 8시 리마인더 발송
- 최QA: 알림 테스트 환경 세팅 필요 (현재 로컬에서 테스트 불가)

### 4. 버그 수정 (이전 스프린트 이월)
- 학습 기록 저장 후 홈 화면 새로고침이 안 되는 버그 (CS 리포트 3건)
- 박백엔드: 원인 파악됨, 이번 스프린트에서 수정 예정

## 결정 사항
- AI 코치 Alpha 출시 범위: 탭 추가 + 코치 메인 화면 + API 연동 + 알림 1종(주간 계획)
- 나머지 알림(저녁 리마인더)은 Beta로 이월
- 스프린트 기간: 7월 21일 ~ 8월 3일 (2주)

## 다음 회의
- 중간 점검: 7월 28일 오전 10시
```

**프롬프트**:

```
위 회의록에서 JIRA 티켓 초안을 추출해줘.

맥락:
- 에픽: EP-023 AI 학습 코치
- 스프린트: Sprint 20 (7/21 ~ 8/3)
- 팀원: 이프론트(FE), 박백엔드(BE), 최QA(QA)

우선순위 기준:
- Highest: Alpha 출시 블로킹
- High: Alpha 범위 내 작업
- Medium: Beta로 이월 가능
- Low: 기술 부채 or 편의 개선

각 티켓 형식:
## [제목]
- 타입 / 우선순위 / 담당자 / 스토리포인트(TBD 가능)
- 설명 (2문장)
- 인수 조건 2~3개
- 에픽: EP-023
```

생성된 티켓을 검토하고 다음을 확인하세요:
- 회의에서 나온 모든 항목이 티켓으로 만들어졌는가?
- "Beta 이월" 결정이 반영됐는가?
- 인수 조건이 구체적인가?

### 실습 2. 티켓 품질 개선

실습 1에서 나온 티켓 초안에 품질 개선 프롬프트를 적용하세요:

```
위 티켓 초안을 개선해줘.

개선 항목:
1. 제목 중 명사 나열인 것을 "동사+목적어" 형태로 교체 (예: "알림 기능" → "AI 코치 주간 학습 알림 발송 구현")
2. 인수 조건에 "제대로", "정상적으로" 같은 모호한 표현을 구체적 기준으로 교체
3. 스토리포인트가 TBD인 것에 대해 1~8 범위에서 초기 추정값 제안 (이유 한 줄 포함)
4. 결정된 "Beta 이월" 항목에 "이번 스프린트 제외" 메모 추가
```

### 실습 3. 자신의 최근 회의록으로 적용

준비해온 실제 회의록이 있다면 지금 적용해보세요.

없다면 다음 짧은 메모를 소재로 사용하세요:

```
오늘 논의:
- 로그인 화면 디자인 개편 (박디자인이 시안 3개 가져옴, 안 B로 결정)
- 네이버 소셜 로그인 추가 요청 들어옴 (이번 분기 가능한지 검토 필요)
- 비밀번호 찾기 이메일이 스팸함으로 가는 문제 (CS 5건, 이프론트 확인 예정)
- 다음 주 화요일 스프린트 리뷰 오후 3시
```

## 핵심 포인트

1. 회의록을 JIRA 티켓으로 변환할 때 **맥락(에픽, 팀원, 우선순위 기준)을 프롬프트에 포함**하면 결과가 훨씬 실용적입니다
2. **타입 구분** (Story/Task/Bug/Spike)을 명확히 하면 개발팀의 백로그 관리가 쉬워집니다
3. Copilot이 자주 만드는 실수는 **모호한 인수 조건**과 **너무 큰 티켓(분할 필요)**입니다. 생성 후 반드시 확인하세요
4. **품질 개선 후속 프롬프트**를 한 번 더 돌리는 것이 초안을 처음부터 다시 쓰는 것보다 훨씬 빠릅니다
5. 티켓 생성 후 **"결정된 이월 항목이 반영됐는가"** 확인은 PM이 직접 해야 합니다. Copilot이 회의 맥락을 완전히 이해하지 못할 수 있습니다
