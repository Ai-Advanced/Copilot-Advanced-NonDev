# PM / 기획자 프롬프트 치트시트

> 복사해서 바로 쓰세요. `[대괄호]` 부분만 여러분 상황에 맞게 교체하면 됩니다.
> 카테고리별로 정리되어 있습니다.

## 1. PRD / 기획서 작성

### 1-1. PRD 초안 골격 생성

**이럴 때 쓰세요**: 새 기능/제품 기획을 시작할 때, 빈 화면 앞에서 막막할 때

```
[제품명]의 [기능명] 기능에 대한 PRD 초안을 Markdown으로 작성해줘.

제품 개요: [한 줄 설명]
기능 목적: [이 기능이 해결하는 문제]
주요 사용자: [대상 사용자]

다음 섹션 포함:
1. 배경 및 문제 정의
2. 목표 (성공 지표 포함)
3. 사용자 스토리 요약 (5개)
4. 기능 명세 (상세 요구사항)
5. 비기능 요구사항 (성능/보안/접근성)
6. 스코프 (In-Scope / Out-of-Scope)
7. 리스크
8. 출시 일정 (마일스톤 표)

각 섹션은 ### 제목으로 구분.
```

---

### 1-2. 문제 정의 섹션 강화

**이럴 때 쓰세요**: 배경/문제 섹션이 너무 피상적으로 느껴질 때

```
아래 PRD의 "배경 및 문제 정의" 섹션을 강화해줘.

현재 버전:
[현재 작성한 문제 정의 붙여넣기]

개선 방향:
- Why now (왜 지금인가) 추가
- 정량적 데이터나 가설적 수치로 문제의 규모 구체화
- 사용자 페인포인트를 인용문 형식으로 1~2개 추가
- 해결하지 않았을 때의 리스크 서술
```

### 1-3. 성공 지표 (KPI) 정의

**이럴 때 쓰세요**: "성공 기준이 뭐야?"라는 질문에 막힐 때

```
[기능명] 기능의 성공 지표를 정의해줘.

기능 설명: [간략히]
주요 목적: [전환율 향상 / 이탈률 감소 / 사용 시간 증가 등]

다음 형식으로 작성:
- 1차 지표 (Primary Metric): 1개, 직접적 성공 측정
- 2차 지표 (Secondary Metrics): 2~3개, 보완적 측정
- 가드레일 지표 (Guardrail Metrics): 악화되면 안 되는 지표 2개
- 각 지표의 현재 baseline과 목표치 (가설적으로 설정 가능)

표 형식으로 정리.
```

### 1-4. 스코프 명확화

**이럴 때 쓰세요**: 개발팀과 "이거 포함이야 아니야?" 논쟁을 피하고 싶을 때

```
아래 기능 기획의 In-Scope / Out-of-Scope를 명확히 정의해줘.

기능 개요: [붙여넣기]

출력 형식:
## In-Scope (이번 버전에 포함)
- [항목] — [이유]

## Out-of-Scope (이번 버전 제외)
- [항목] — [제외 이유 또는 향후 버전 고려]

## 전제 조건 (Dependencies)
- [항목]

경계가 애매한 항목은 "⚠️ 논의 필요"로 표시.
```

### 1-5. 리스크 분석

**이럴 때 쓰세요**: PRD 리스크 섹션이 항상 비어있을 때

```
[기능명] 기능의 출시 리스크를 분석해줘.

기능 요약: [1~2문장]
출시 일정: [날짜]

다음 관점에서 각 3개씩 리스크 도출:
1. 기술적 리스크 (개발 복잡도, 의존성)
2. 사용자 경험 리스크 (혼란, 이탈)
3. 비즈니스 리스크 (매출 영향, 경쟁사)
4. 운영 리스크 (CS 문의 증가, 인프라)

각 리스크에 대해: 발생 가능성(High/Medium/Low), 영향도(High/Medium/Low), 대응 방안 포함.
표 형식으로 정리.
```

### 1-6. PRD 검토 요청

**이럴 때 쓰세요**: 작성한 PRD의 구멍을 찾고 싶을 때

```
아래 PRD를 시니어 PM 관점에서 검토하고 개선점을 알려줘.

검토 관점:
1. 논리 흐름 (문제 → 솔루션 → 지표가 연결되는가)
2. 누락된 엣지케이스
3. 개발팀이 오해할 수 있는 모호한 표현
4. 사용자 스토리가 INVEST 원칙을 만족하는가
5. 성공 지표가 측정 가능한가

출력: 문제점 목록 + 각 개선안

[--- PRD 붙여넣기 ---]
```

## 2. 사용자 스토리 & 요구사항

### 2-1. 사용자 스토리 대량 생성

**이럴 때 쓰세요**: 기능 하나의 스토리를 빠르게 많이 뽑아야 할 때

```
[기능명] 기능의 사용자 스토리를 작성해줘.

사용자 유형: [예: 일반 회원, 관리자, 비로그인 방문자]
기능 목적: [기능 설명]

다음 형식으로 최소 15개 작성:
As a [사용자 유형], I want to [행동], so that [이유/가치].

포함 카테고리:
- 정상 흐름 (Happy Path) 스토리
- 엣지케이스 스토리
- 에러 처리 스토리
- 권한/보안 관련 스토리

INVEST 원칙(Independent, Negotiable, Valuable, Estimable, Small, Testable) 체크 후 각 스토리에 위반 여부 표시.
```

### 2-2. Gherkin 형식 변환

**이럴 때 쓰세요**: QA팀 또는 개발팀과 인수 조건을 명확히 공유할 때

```
아래 사용자 스토리를 Gherkin(Given-When-Then) 형식의 인수 조건(Acceptance Criteria)으로 변환해줘.

사용자 스토리: [붙여넣기]

출력 형식:
```gherkin
Feature: [기능명]

  Scenario: [시나리오 이름]
    Given [초기 상태]
    When [사용자 행동]
    Then [기대 결과]

  Scenario: [엣지케이스 이름]
    ...
```

시나리오는 정상 흐름 1개, 엣지케이스 2개 이상 포함.
```

### 2-3. 요구사항 우선순위 MoSCoW 분류

**이럴 때 쓰세요**: 요구사항 목록이 있는데 우선순위를 못 정했을 때

```
아래 요구사항 목록을 MoSCoW 방식으로 분류해줘.

제품 목표: [핵심 목표]
출시 기한: [날짜]
개발 리소스: [예: 개발자 3명, 4주]

요구사항 목록:
[번호 매긴 요구사항 목록 붙여넣기]

분류 기준:
- Must Have: 없으면 출시 불가
- Should Have: 중요하지만 없어도 출시는 가능
- Could Have: 시간 되면 좋음
- Won't Have (이번 버전): 의도적으로 제외

각 분류 이유도 한 줄씩 설명.
```

### 2-4. 엣지케이스 발굴

**이럴 때 쓰세요**: "QA에서 버그 나왔는데 기획서에 없었어요"를 예방하고 싶을 때

```
아래 기능 기획에서 PM이 놓치기 쉬운 엣지케이스를 모두 찾아줘.

기능 설명: [붙여넣기]

다음 관점에서 각 3개 이상 엣지케이스 도출:
1. 입력값 이상 (비어있음, 너무 길다, 특수문자, 한글/영문/숫자 혼합)
2. 권한 경계 (비로그인, 권한 없는 사용자, 다른 사용자의 데이터)
3. 동시성 (두 명이 동시에 같은 항목 수정)
4. 네트워크/성능 (느린 연결, 요청 중 페이지 이탈)
5. 비즈니스 규칙 경계 (최솟값, 최댓값, 특수 상태)

각 엣지케이스를 "시나리오: [설명] / 기대 동작: [설명]" 형식으로.
```

### 2-5. 요구사항 명세서 정리

**이럴 때 쓰세요**: 산발적으로 모인 요구사항을 체계적으로 정리해야 할 때

```
아래 산발적인 요구사항들을 체계적인 기능 요구사항 명세서로 정리해줘.

원본 요구사항 (회의록/메모 등):
[붙여넣기]

출력 형식:
- 요구사항 ID: REQ-001 형식
- 분류: 기능적(Functional) / 비기능적(Non-Functional)
- 우선순위: 높음/중간/낮음
- 설명: 명확한 1~2문장
- 인수 조건: 1~3개

표 형식으로 정리. 중복 요구사항은 통합.
```

## 3. 회의록 & 이해관계자 커뮤니케이션

### 3-1. 회의록 구조화

**이럴 때 쓰세요**: 회의 후 메모를 정식 회의록으로 만들 때

```
아래 회의 메모를 정식 회의록 Markdown 형식으로 구조화해줘.

회의 정보:
- 일시: [날짜/시간]
- 참석자: [이름 목록]
- 주제: [회의 주제]

원본 메모:
[메모 붙여넣기]

출력 섹션:
1. 회의 목적 (1~2문장)
2. 논의 내용 (안건별 요약)
3. 결정 사항 (결정된 것만, 불릿 형식)
4. 액션 아이템 (담당자 / 기한 / 내용, 표 형식)
5. 다음 회의 안건 후보
```

---

### 3-2. 회의록 → JIRA 티켓 변환

**이럴 때 쓰세요**: 회의 후 JIRA 입력이 귀찮을 때

```
아래 회의록에서 JIRA 티켓으로 만들어야 할 항목들을 추출해줘.

회의록:
[붙여넣기]

각 티켓을 다음 형식으로:
## [티켓 제목]
- **타입**: Story / Task / Bug / Spike 중 하나
- **우선순위**: Highest / High / Medium / Low
- **담당자**: [이름 또는 "논의 필요"]
- **스토리 포인트**: [1~13 피보나치, 불확실하면 "TBD"]
- **설명**: 2~3문장
- **인수 조건**: 2~3개 불릿
- **라벨**: [관련 컴포넌트/팀]
```

### 3-3. 임원 보고용 요약 변환

**이럴 때 쓰세요**: 상세 기획서를 임원이 5분 안에 읽을 수 있는 버전으로 줄일 때

```
아래 기획서/PRD를 임원 보고용 1페이지 요약으로 변환해줘.

원본:
[붙여넣기]

요구사항:
- A4 1페이지 이내 (약 500자)
- 숫자/지표 중심으로 임팩트 강조
- 기술 용어 최소화
- 톤: 자신감 있고 명확하게
- 구조: 문제 → 해결책 → 기대 효과 → 요청사항(의사결정 필요한 것)
```

### 3-4. 개발팀 전달용 기술 스펙 정리

**이럴 때 쓰세요**: 기획 의도를 개발팀이 오해 없이 받을 수 있도록 할 때

```
아래 기능 기획을 개발팀 전달용 기술 스펙 문서로 변환해줘.

원본 기획:
[붙여넣기]

포함할 내용:
1. API 엔드포인트 목록 (추정, 확정은 개발팀 몫)
2. 데이터 모델 변경 사항 (추가/수정될 필드)
3. 예외 처리 케이스별 HTTP 상태 코드 제안
4. 성능 요구사항 (응답 시간, 동시 사용자 수)
5. 보안 고려사항

각 항목이 "기획 의도"임을 명시하고, 개발팀이 상세 설계를 해야 함을 주석으로 표기.
```

## 6. 스프린트 & 백로그 관리

### 6-1. 에픽 분해 (Epic → Story)

**이럴 때 쓰세요**: 큰 에픽을 스프린트에 넣을 수 있는 크기로 쪼갤 때

```
아래 에픽을 2주 스프린트에 들어갈 수 있는 사용자 스토리로 분해해줘.

에픽: [에픽 제목과 설명]
팀 규모: [개발자 N명]
스프린트 용량: [대략적인 스토리 포인트 합계]

분해 기준:
- 각 스토리는 독립적으로 완료 가능해야 함
- 각 스토리는 사용자에게 가시적인 가치를 제공해야 함
- 스토리 포인트 1~8 범위
- 기술 작업(Task)은 별도로 분리

출력: 스토리 목록 + 추정 포인트 + 의존성 표시
```

### 6-2. 스프린트 목표 작성

**이럴 때 쓰세요**: 스프린트 플래닝 때 명확한 목표 문장이 필요할 때

```
아래 스프린트 백로그를 기반으로 스프린트 목표(Sprint Goal)를 작성해줘.

### 7-2. A/B 테스트 설계

**이럴 때 쓰세요**: A/B 테스트를 기획할 때 실험 설계를 도와줄 때

```

가설: [예: 버튼 색상을 파란색으로 바꾸면 클릭률이 올라간다]
현재 상황: [baseline 데이터 또는 추정]
목표 지표: [Primary Metric]

설계 요소:
1. 실험 가설 명확화 (만약 A를 하면 B가 C% 향상될 것이다)
2. 대조군(A) vs 실험군(B) 정의
3. 샘플 크기 추정 (유의수준 0.05, 검정력 0.8 기준)
4. 실험 기간 제안
5. 성공 기준
6. 잠재적 혼재변수(confounding variable)
```
