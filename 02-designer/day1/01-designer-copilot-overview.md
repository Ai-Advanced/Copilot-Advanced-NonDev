# 01. 디자이너를 위한 Copilot 개요

## 학습 목표

- Copilot이 디자이너 업무 흐름에서 정확히 어느 위치에 들어오는지 파악
- Copilot이 돕는 12가지 디자이너 업무를 구체적으로 이해
- Before/After 비교 3가지로 실질적 시간 절감 감각 익히기
- "Figma를 대체하지 않는다"의 의미를 명확히 정립

**예상 소요**: 40분

---

## 1.1 먼저 명확히 — Copilot은 Figma 대체재가 아닙니다

이 질문을 먼저 짚고 넘어가겠습니다.

> "Copilot이 있으면 Figma 안 써도 되나요?"

**아니요.** 완전히 다른 도구입니다.

| 도구 | 역할 | 강점 |
|------|------|------|
| **Figma** | 시각적 디자인, 프로토타이핑, 협업 | 픽셀 정밀도, 컴포넌트 라이브러리, 디자이너 협업 |
| **Copilot** | 텍스트/코드/JSON 생성 및 변환 | 반복 문서화, 토큰 코드화, CSS 번역, 스펙 작성 |

두 도구는 **서로 다른 단계**에서 쓰입니다.

```
디자인 프로세스에서의 위치:

Research → Wireframe → [Figma: 시각 디자인] → [Copilot: 코드화/문서화] → 개발 → 출시
```

Copilot은 Figma에서 나온 결과물을 **개발 팀에 전달하는 과정**을 돕습니다.

---

## 1.2 Copilot이 돕는 12가지 디자이너 업무

### 카테고리 1. 디자인 시스템 관리

**업무 1: 디자인 토큰 JSON 생성 및 관리**

Figma의 Variables/Styles를 코드로 옮기는 작업. 수작업으로는 오타와 누락이 생기고, 다크모드까지 추가하면 두 배로 복잡해집니다.

```
이전 방식: Figma Styles 화면 보면서 손으로 JSON 타이핑 (30분+)
Copilot: "Primary #2563EB → 10단계 스케일 토큰 JSON" → 30초
```

**업무 2: 다크모드 토큰 변환**

라이트모드 토큰이 있을 때, 다크모드 대응값을 WCAG 대비율을 유지하면서 자동 생성.

**업무 3: Style Dictionary CSS 변환**

토큰 JSON → CSS custom properties, SCSS variables, JavaScript constants 등 여러 형식으로 자동 변환.

---

### 카테고리 2. 개발자 핸드오프

**업무 4: 컴포넌트 스펙 문서 작성**

Props, States, Variants, 접근성 요건을 표 형식으로 정리한 스펙 문서. Notion이나 Confluence에 올리는 handoff 문서를 Copilot이 초안 작성.

**업무 5: CSS 스펙 추출**

"패딩 24px, 모서리 12px, 그림자 이렇게 줘" 식의 설명을 실제 CSS로 번역.

**업무 6: 디자인 QA 체크리스트 생성**

화면별 QA 항목을 자동 생성. 레이아웃, 타이포, 색상, 상태, 반응형, 접근성을 망라.

---

### 카테고리 3. 프로토타입 제작

**업무 7: HTML/CSS 클릭 가능 프로토타입**

Figma 프로토타입은 링크 클릭 정도만 가능하지만, HTML 프로토타입은 실제 CSS 애니메이션, 반응형, 폼 인터랙션까지 가능. 개발팀에 "이게 원하는 느낌입니다" 전달 시 매우 효과적.

**업무 8: 랜딩 페이지 프로토타입**

마케팅팀과 협업 시, 간단한 랜딩 페이지를 빠르게 만들어 의견 수렴 후 개발에 넘기는 방식.

---

### 카테고리 4. 접근성 검토

**업무 9: 색 대비 계산 및 대안 제시**

WCAG 2.1 AA 기준 색 대비율 계산, 실패한 조합에 대한 대안 색상 제안.

**업무 10: ARIA 속성 추가**

HTML에 role, aria-label, aria-expanded 등 접근성 속성 자동 추가.

---

### 카테고리 5. 콘텐츠 & 문서화

**업무 11: UI 카피 배리에이션**

버튼 레이블, 에러 메시지, 툴팁 텍스트의 여러 버전을 빠르게 생성해서 A/B 테스트나 의사결정에 활용.

**업무 12: 이미지 최적화 스크립트**

여러 이미지를 WebP로 변환하거나, 특정 디렉토리의 이미지 파일을 일괄 리사이즈하는 스크립트 생성.

---

## 1.3 Before/After 비교 3가지

### Before/After 1. 디자인 토큰 작성

**상황**: 새 브랜드의 컬러 시스템을 코드로 옮겨야 합니다. Primary 색상 1개로 시작해서 10단계 스케일 + 시맨틱 토큰 + 다크모드까지.

**Before (Copilot 없이)**

```
1. Figma Styles 패널 열기
2. 각 색상의 hex 값 수동으로 기록
3. JSON 형식 구글링
4. 손으로 타이핑:
   "primary-50": "#EFF6FF",
   "primary-100": "#DBEAFE",
   ... (10개)
5. 시맨틱 토큰 별도 작성
6. 다크모드 값 다시 결정하고 작성
7. 오타 검토

소요 시간: 약 45분
오타 발생 확률: 높음
```

**After (Copilot과 함께)**

```
프롬프트:
Primary #2563EB 기준 10단계 컬러 스케일 + semantic 토큰
(text-primary/bg-default/border-default/brand-default)
다크모드 포함, W3C DTCG JSON, JSON만 반환.

소요 시간: 2분 (프롬프트 작성 + 검토)
결과: 완전한 JSON, 즉시 사용 가능
```

**절감**: 43분 → 반복 업무마다 누적

---

### Before/After 2. 컴포넌트 스펙 문서

**상황**: Button 컴포넌트 스펙을 개발팀에 넘겨야 합니다. Props, Variants, States, 접근성 요건 포함.

**Before (Copilot 없이)**

```
1. Notion/Confluence 새 페이지 생성
2. Props 테이블 수동 작성
   - 이름, 타입, 기본값, 설명 열 만들기
   - variant props 나열 (primary/secondary/ghost/danger)
   - size props 나열 (sm/md/lg)
   - 상태 props (disabled, loading)
3. Variants 표 작성
4. States 표 작성 (hover, focus, active, disabled)
5. 접근성 요건 구글링 후 작성
6. DO/DON'T 직접 생각해서 작성

소요 시간: 2~3시간
```

**After (Copilot과 함께)**

```
프롬프트:
Button 컴포넌트 스펙 Markdown 문서:
- Props 표: 이름/타입/기본값/필수/설명
- Variants: primary/secondary/ghost/danger/link
- States: default/hover/focus/active/disabled/loading
- 접근성: ARIA 속성, 키보드 동작
- DO/DON'T 5가지씩
- 개발자 handoff 수준 상세도

결과: 90% 완성 초안 5분 안에
남은 작업: Figma 링크 추가, 실제 브랜드 색상값 교체, 검토
실질 소요: 20분
```

**절감**: 2~3시간 → 20분

---

### Before/After 3. HTML 프로토타입

**상황**: 새 대시보드 레이아웃을 이해관계자에게 보여줘야 합니다. Figma 링크를 공유했더니 "실제로 어떻게 움직이는지 보고 싶다"는 피드백.

**Before (Copilot 없이)**

```
옵션 A: 개발팀에 의뢰
→ 대기 시간 3~5일, 개발자 리소스 소모

옵션 B: 직접 만들기
→ HTML/CSS를 잘 모르면 반나절이상 소요
→ 반응형, 애니메이션 추가하면 하루+
```

**After (Copilot과 함께)**

```
프롬프트:
SaaS 대시보드 레이아웃 HTML/CSS:
- 좌측 사이드바 240px (로고, 메뉴 5개, 하단 프로필)
- 우측 메인 영역 (상단 헤더 + 콘텐츠 영역)
- 메인에 통계 카드 4개 (2x2 그리드)
- 반응형: 모바일에서 사이드바 숨김
- CSS variables로 색상 관리
- Live Server로 바로 열 수 있게

소요 시간: 30분 (프롬프트 + 조정 + 확인)
결과: 브라우저에서 실제로 작동하는 프로토타입
```

**절감**: 3~5일(개발 의뢰) 또는 반나절(직접) → 30분

## 1.4 Copilot 작동 방식 이해 (디자이너 관점)

### 맥락이 핵심

Copilot은 **현재 열린 파일의 내용을 읽고** 맥락을 파악합니다. 이게 ChatGPT와 결정적으로 다른 점입니다.

```
예시:
tokens.json 파일에 이미 컬러 토큰이 있고,
그 아래에 커서를 두고 "spacing 토큰 추가해줘"라고 하면,
Copilot은 이미 있는 JSON 구조 스타일을 유지하며 spacing 토큰을 추가합니다.
```

### 반복 패턴을 잘 학습

토큰 파일처럼 패턴이 반복되는 파일에서 Copilot은 특히 빛납니다.

```json
{
  "primary": {
    "100": { "$type": "color", "$value": "#DBEAFE" },
    "200": { "$type": "color", "$value": "#BFDBFE" },
    "300": { /* 여기서 Tab 누르면 자동 완성 */ }
  }
}
```

### 3가지 활용 모드 요약

| 모드 | 사용법 | 디자이너 최적 상황 |
|------|--------|------------------|
| **Tab 자동완성** | 코드 입력 중 Tab | JSON 토큰 패턴 반복, CSS 속성 |
| **Inline Chat** | `Ctrl+I` | 기존 CSS 수정, 특정 부분 변환 |
| **Chat 사이드바** | `Ctrl+Alt+I` | 새 파일 생성, 긴 스펙 문서 |

## 핵심 포인트

1. **Copilot은 Figma 대체재가 아님** — 디자인 → 코드화/문서화 단계를 담당
2. **12가지 업무** 중 내 업무에 해당하는 것을 파악하는 것이 첫 번째 단계
3. **Before/After 3가지**: 토큰 45분 → 2분, 스펙 3시간 → 20분, 프로토타입 3일 → 30분
4. **맥락 인식**: 열린 파일을 읽으므로, 기존 구조가 있을수록 더 정확한 결과
5. **Tab, Inline Chat, Chat 사이드바** 3가지 모드를 업무에 따라 선택
