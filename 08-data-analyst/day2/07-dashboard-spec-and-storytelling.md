# 07. 대시보드 스펙 문서화 + 인사이트 스토리텔링

## 학습 목표

- BI 도구(Tableau/Looker/Metabase/Superset)용 대시보드 스펙 문서를 Copilot으로 빠르게 작성
- 사용자 여정 기반 대시보드 설계 원칙 이해
- 숫자 나열이 아닌 인사이트 스토리로 변환하는 프롬프트 패턴 체득
- 지표 정의서 작성 자동화
- 실습: "구독 서비스 운영 현황 대시보드" 스펙 문서 완성

**예상 소요**: 45분

---

## 7.1 대시보드 스펙 문서가 필요한 이유

분析가가 대시보드 개발자(또는 BI 엔지니어)에게 요청할 때, 말로 설명하면 오해가 생깁니다.

**말로만 요청했을 때**:
- "이탈률 차트 넣어주세요" → "어떤 기간? 어떤 필터? 어떤 분모?"
- 주고받기 3~4회, 결국 원하는 것과 다른 차트가 나옴

**스펙 문서가 있을 때**:
- 차트 유형, 데이터 소스, 집계 방식, 필터 조건, 업데이트 주기가 명확
- 오해 없이 한 번에 구현

스펙 문서는 **분析가와 BI 엔지니어 사이의 계약서**입니다.

---

## 7.2 대시보드 설계 원칙: 사용자 여정 기반

차트를 나열하는 것이 아니라, **"누가 어떤 질문에 답하기 위해 이 대시보드를 보는가"** 에서 시작합니다.

### 사용자별 질문 매핑

| 사용자 | 질문 | 필요한 차트 |
|--------|------|-----------|
| CEO | "성장하고 있나? 이탈은 괜찮나?" | KPI 카드, MRR 트렌드 |
| PM | "어느 단계에서 사용자를 잃고 있나?" | 퍼널 차트, 코호트 리텐션 |
| 마케터 | "어떤 채널이 효율적인가?" | 채널별 신규 가입, CAC |
| CS 팀장 | "이탈이 언제 가장 많이 발생하나?" | 이탈 시점 분포, 이탈 세그먼트 |

### 대시보드 레이아웃 원칙

```
상단: KPI 카드 (숫자 4개 — 가장 먼저 보는 것)
중단: 트렌드 + 코호트 (시간 흐름 파악)
하단: 세그먼트 분解 + 상관 (원인 탐색)
```

## 7.3 대시보드 스펙 문서 구조

각 차트에 대해 아래 항목을 정의합니다.

| 항목 | 설명 |
|------|------|
| 차트 ID | 고유 식별자 (예: CHART-001) |
| 차트명 | 사람이 읽는 이름 |
| 차트 유형 | KPI 카드 / 라인 차트 / 바 차트 / 히트맵 등 |
| 목적 | 이 차트가 답하는 질문 |
| 데이터 소스 | 테이블명, 필요 컬럼 |
| 집계 방식 | COUNT / SUM / AVG / 비율 등 |
| 시간 입도 | 일별 / 주별 / 월별 |
| 필터 | 기본 필터 조건, 사용자 선택 필터 |
| 업데이트 주기 | 실시간 / 일별 / 주별 |
| 드릴다운 | 클릭 시 상세 뷰 여부 |

## 7.4 Copilot으로 스펙 문서 초안 생성

### 프롬프트 1. 전체 대시보드 구조 생성

```
"구독 서비스 운영 현황 대시보드" 스펙 문서를 Markdown으로 작성해줘.

대상 독자: 제품팀 리드, COO
사용 BI 도구: Tableau (또는 Looker, Metabase 중 하나 선택)
분析 대상: 신규 가입, MRR, 리텐션, 이탈, 퍼널

포함할 차트 (각각 아래 항목 포함):
1. KPI 카드 4개 (신규 가입 / MRR / 30일 리텐션 / 이탈률)
2. MRR 월별 트렌드 (12개월)
3. 코호트 리텐션 히트맵 (최근 6개월 코호트)
4. 가입 퍼널 전환율
5. plan별 구독자 분포 (도넛 차트)
6. 이탈 사용자 구독 기간 분포 (히스토그램)

각 차트별 항목:
- 차트 ID, 차트명, 차트 유형, 목적(질문)
- 데이터 소스 (테이블명, 컬럼명)
- 집계 방식
- 기본 필터 / 사용자 선택 필터
- 업데이트 주기

형식: Markdown 테이블 + 섹션 구조
```

### 프롬프트 2. Tableau 계산 필드 정의

```
Tableau용 대시보드에서 필요한 계산 필드(Calculated Field) 목록을 작성해줘.

필요한 지표:
- MRR: SUM([mrr]) — subscriptions 테이블, 월 마지막 날 기준
- 30일 리텐션율: 가입 후 30일 이내 재접속 사용자 비율
- 이탈률: COUNTD([user_id where event_type='cancel']) / COUNTD([전체 구독 중 user_id])
- LTV: SUM([amount]) per user_id, 평균값
- CAC: 마케팅 예산 / 신규 가입자 수 (별도 비용 테이블 필요)

각 계산 필드:
- 필드명 (영문)
- 공식 (Tableau 문법)
- 설명 (한국어)
- 주의사항
```

### 프롬프트 3. Looker LookML 스펙 초안

```
다음 지표를 Looker LookML 형식으로 정의하는 dimension/measure 초안 작성.
뷰 이름: subscriptions

지표:
1. new_subscribers: 신규 subscribe 이벤트 수 (type: count_distinct, user_id 기준)
2. churned_users: cancel 이벤트 고유 사용자 수
3. mrr_total: mrr 컬럼 합계 (type: sum)
4. retention_30d: 가입 30일 이내 재활동 비율 (type: number, 커스텀 SQL)

각 measure에 description, value_format_name, filters 포함.
```

### 프롬프트 4. Metabase / Superset 쿼리 스펙

```
Metabase (또는 Superset)에서 아래 차트를 만들기 위한 SQL 쿼리를 작성해줘.

차트: "월별 plan별 신규 구독자 스택 바 차트"
데이터 소스: PostgreSQL
필요 컬럼: year_month, plan, new_subscribers
집계: month 기준 plan별 COUNT(DISTINCT user_id)
필터: event_type = 'subscribe', 최근 12개월
정렬: year_month ASC

Metabase Native Query 형식 ({{}} 변수 사용).
```

## 7.5 지표 정의서 자동화

지표 정의가 팀마다 달라서 생기는 혼란은 **공식 지표 정의서** 하나로 해결합니다.

### 프롬프트: 지표 정의서 일괄 생성

```
다음 8개 지표의 공식 정의서를 Markdown 테이블 형식으로 작성해줘.

지표 목록:
MRR, ARR, 이탈률(Churn Rate), NRR(Net Revenue Retention),
30일 리텐션율, LTV, CAC, 퍼널 전환율

각 지표 항목:
| 지표명 | 영문명 | 정의 (한 문장) | 계산 공식 | 단위 | 측정 주기 | 데이터 소스 | 경계 조건 |

경계 조건 예시:
- 이탈률: 테스트 계정, 환불 내 해지, 비자발적 해지(결제 실패) 포함/제외 여부
- LTV: 환불 금액 포함/제외, 기간 제한(12개월 LTV vs. 전체)
```

### 완성된 지표 정의서 예시

| 지표명 | 영문명 | 정의 | 계산 공식 | 단위 | 측정 주기 | 데이터 소스 |
|--------|--------|------|---------|------|---------|-----------|
| MRR | Monthly Recurring Revenue | 특정 월에 구독에서 발생하는 월 반복 수익 | SUM(mrr) WHERE event_type IN ('subscribe','upgrade','downgrade') AND month = 대상월 | USD | 월별 | subscriptions.mrr |
| 이탈률 | Churn Rate | 월초 구독자 중 해당 월에 해지한 비율 | 해지 사용자 수 / 월초 구독자 수 × 100 | % | 월별 | subscriptions |
| 30일 리텐션 | 30d Retention | 가입 후 30일 이내에 재사용한 사용자 비율 | 30일 내 재활동 / 코호트 크기 × 100 | % | 코호트별 | events, users |

## 7.6 인사이트 스토리텔링

### 숫자 나열 vs 스토리

**나쁜 예 (숫자 나열)**:
```
3월 신규 가입자: 31,240명
3월 이탈률: 8.3%
3월 MRR: $482,301
3월 리텐션: 61.3%
```

**좋은 예 (스토리)**:
```
3월 신규 가입이 31,240명으로 전월 대비 12% 성장했습니다.
리텐션율도 61.3%로 업계 평균(58%)을 3.3%p 상회합니다.
그러나 이탈률이 8.3%로 전월 7.1%에서 1.2%p 악화되었습니다.
특히 가입 30일 이내 이탈이 전체의 44%를 차지하는 점이 우려됩니다.
온보딩 품질 개선이 Q2 최우선 과제로 판단됩니다.
```

두 번째가 더 설득력 있는 이유: **원인과 맥락, 우선순위**가 포함되어 있기 때문입니다.

### 좋은 인사이트의 3요소

1. **숫자 (What)**: 무슨 일이 일어났는지
2. **맥락 (So What)**: 이게 왜 중요한지 (목표 대비, 전월 대비, 업계 대비)
3. **액션 (Now What)**: 무엇을 해야 하는지

### Copilot으로 인사이트 생성하기

**프롬프트 공식**:
```
다음 분析 결과를 바탕으로 [대상]을 위한 [형식] 인사이트 작성.

분析 결과:
[수치 목록]

작성 원칙:
- 수치 반드시 포함 (%, 절대값 모두)
- "것으로 보입니다", "추정됩니다" 같은 모호한 표현 금지
- 긍정/우려/액션 3파트 구조
- [길이] 이내
```

### 인사이트 품질 체크리스트

- [ ] 모든 수치가 실제 분析 결과와 일치하는가
- [ ] 모호한 표현("다소", "약간", "것으로 보임")이 없는가
- [ ] 권고 액션이 분析 결과에서 논리적으로 도출되는가
- [ ] 경쟁사/외부 데이터를 근거 없이 주장하지 않는가
- [ ] 독자(CEO vs PM vs CS)에 맞는 수준인가

## 7.8 BI 도구별 스펙 작성 차이

### Tableau

- **계산 필드**: 복잡한 지표는 Tableau Calculated Field로 정의 (LOD 표현식 필요 여부 명시)
- **데이터 소스**: Live Connection vs Extract 선택 기준 명시
- **퍼블리시**: Tableau Server/Public 공유 여부

### Looker (Google)

- **LookML**: View, Measure, Dimension을 코드로 정의 (버전 관리 가능)
- **Explore**: 어떤 Explore를 기반으로 할지
- **필터 타입**: `filter_type: date` / `string` 등

### Metabase

- **Native Query**: 복잡한 집계는 SQL로 직접 작성
- **Variables**: `{{date_filter}}` 같은 변수로 필터 연동
- **Collection**: 어느 Collection에 위치할지

### Superset

- **Dataset**: SQL Lab에서 Virtual Dataset 생성 여부
- **Chart type**: 지원하는 차트 타입 목록 확인 (Metabase와 다름)
- **Filter Box**: Dashboard Native Filter 설정

## 핵심 포인트

1. **스펙 문서 = 계약서**: 차트 유형·집계·필터를 명확히 정의하면 구현 오해가 없어짐
2. **사용자 여정 먼저**: "누가 어떤 질문에 답하기 위해 보는가"에서 차트 목록 도출
3. **인사이트 3요소**: What(숫자) + So What(맥락) + Now What(액션)
4. **모호한 표현 금지**: "것으로 보임", "다소", "약간"은 신뢰를 깎음. 수치로 대체
5. **지표 정의서 공유**: 팀 내 "이탈률"의 정의가 다르면 아무리 좋은 차트도 혼란. 한 번 정의하고 전체 공유
